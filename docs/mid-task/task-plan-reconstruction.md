## 2. 项目总目标重建

结合现有代码和文档，这个项目的真实目标并不是做一个工业级 LSM-Tree 存储系统，而是做一个：

- 面向教学与毕业设计展示的 LSM-Tree 可视化模拟系统
- 能展示从写入到落盘、再到 compaction 的核心机制
- 能比较 STC 与 LCS 两种 compaction 策略差异
- 能通过前端、metrics、trace 和实验脚本形成“可观察、可复现、可分析”的闭环

因此，最可能的总目标可以重建为：

1. 先实现最小 LSM 核心机制
2. 再实现策略差异与可观测性
3. 再把能力包装成可演示系统
4. 最后通过实验和文档把结果讲清楚

这也解释了为什么任务顺序不是“先做界面”，而是先做模型、写路径、落盘、读取、compaction、指标，再做服务化和前端。

## 3. 当时为什么要拆成 11 个 Task

把项目拆成 11 个 task，本质上是在控制三个风险：

### 3.1 控制技术耦合

LSM-Tree 的核心链路天然耦合很强：

- 没有统一模型，后续状态和接口会乱
- 没有写路径，就无法谈 flush
- 没有 SSTable，就无法谈读路径与 Bloom
- 没有 compaction，就无法谈策略对比
- 没有 metrics/trace，就无法谈实验与可视化

所以最合理的方式，就是按依赖链一段一段推进。

### 3.2 控制中期节点风险

毕业设计通常不是等全部做完才第一次展示，而是需要中途有一个“能跑、能讲、能演示”的中期版本。

因此任务拆分必须保证：

- 前几步就能逐渐形成可运行原型
- 到 task8-task10 时已经形成中期答辩可演示闭环
- task11 再把实验和结论补强

### 3.3 控制范围膨胀

从 PR 正文看，每个阶段都写了 `Out of Scope`，这说明当时很明确地在做“范围控制”。

也就是说，这 11 个 task 的设计思路不是“一次性把所有特性都做完”，而是：

- 先做教学型最小必要系统
- 再留出未实现项作为后续扩展和结题提升空间

## 5. 每个 Task 的重建版目标

### task1：项目脚手架与工程基础

重建目标：

- 建立 monorepo 结构
- 明确 backend / frontend / docs / experiments 的职责边界
- 让项目一开始就具备基本运行、构建和部署外壳

预期产出：

- FastAPI 基础服务
- Vue3 前端基础工程
- Docker Compose
- README 初版

依赖关系：

- 为所有后续任务提供工程载体

### task2：统一模型与接口契约

重建目标：

- 统一配置、记录、状态、事件、指标等核心对象的模型定义
- 为序列化、导出、接口交互建立稳定约束

预期产出：

- Pydantic 模型
- dataclass 状态模型
- 验证规则
- 契约文档

依赖关系：

- 为 task3-task11 提供共享数据基础

### task3：写路径第一阶段

重建目标：

- 实现 `put` 的最小闭环
- 让写入先经过 WAL，再进入 MemTable
- 能判断是否需要 flush

预期产出：

- WAL append-only
- MemTable 写入
- `seq` 演进
- flush-needed 判断

依赖关系：

- 是 flush、SSTable、compaction 的前置条件

### task4：flush 与 SSTable 落盘

重建目标：

- 把内存中的数据真正刷写成磁盘上的教学型 SSTable

预期产出：

- Level 0 SSTable 持久化
- metadata 文件
- MemTable 清空
- Level 状态可查询

依赖关系：

- 为读路径和后续 compaction 提供真实对象

### task5：读路径与 Bloom Filter

重建目标：

- 让系统不只会写，也能读
- 让查询链路具备基本的 LSM 查找行为
- 让 Bloom filter 作为教学中可解释的优化点进入系统

预期产出：

- `get(key)` 查询路径
- MemTable + SSTable lookup
- per-SSTable Bloom
- 查询路径记录

依赖关系：

- 为实验中读放大观察提供基础

### task6：STC 压缩框架

重建目标：

- 先实现一种最基础、最容易讲清楚的 compaction 策略
- 建立 compaction 框架，不把逻辑硬编码死

预期产出：

- compaction 基类
- STC 策略
- 同步 compaction 流程
- compaction 历史

依赖关系：

- 为 LCS 对比与后续 metrics 埋点提供基础

### task7：LCS 与策略切换

重建目标：

- 在已有 STC 基础上加入第二种策略
- 让系统具备“可对比性”

预期产出：

- 简化版 LCS
- `stc/lcs` 切换
- 同 workload 下的行为差异

依赖关系：

- 是实验分析成立的关键一步

### task8：metrics 与 trace

重建目标：

- 把系统行为记录下来
- 让后续实验和前端可视化都有统一数据来源

预期产出：

- metrics collector
- trace emitter
- JSON/CSV 导出
- amplification 指标

依赖关系：

- 为 task9 的接口输出和 task10 的前端展示提供数据基础
- 为 task11 的实验分析提供证据基础

### task9：FastAPI 服务化与 WebSocket

重建目标：

- 把 simulator 封装成外部可调用的服务
- 提供答辩时可直接演示的统一入口

预期产出：

- REST API

- API schema
- runtime service

依赖关系：

- 为前端和演示提供交互接口

### task10：Vue 最小演示前端

重建目标：

- 把“能调用的后端”变成“能展示的系统”
- 让中期答辩具备页面级交互界面

预期产出：

- 依赖 task9 的 API/WS

### task11：实验与结果分析

重建目标：

预期产出：

依赖关系：

## 6. 任务之间的真实依赖链

如果把这 11 个 task 画成最简依赖链，可以重建为：

`task1 -> task2 -> task3 -> task4 -> task5 -> task6 -> task7 -> task8 -> task9 -> task10 -> task11`

但更准确的理解应该是：

- `task8` 同时服务于 `task9`、`task10`、`task11`
- `task7` 是 `task11` 能够做“策略对比实验”的前提
- `task10` 不是系统正确性的前提，但它是“中期可演示性”的关键

换句话说，这 11 个 task 不是并列堆积，而是一条非常标准的：

`核心机制 -> 可观测性 -> 服务化 -> 可视化 -> 实验分析`

的演进链。

## 7. 中期阶段大概率原本想达到的状态

根据 task10 和 task11 的位置，可以重建出一个很合理的中期目标：

### 中期前必须完成

- LSM 核心链路能运行
- STC/LCS 都能跑
- metrics/trace 可导出
- 后端可通过 API 调用
- 前端能进行最小化展示

### 中期时重点要讲清楚

- LSM 的写入、落盘、查找、压缩流程
- STC 和 LCS 的差异
- 系统不是黑盒，能通过 trace 和 metrics 观察
- 实验结果是可复现的

### 中期时可以接受暂时不做

- tombstone
- range query
- WAL recovery
- 工业级调度
- 精细化前端美化

这与现有代码和文档的状态完全一致，说明当前重建出的任务规划是自洽的。

## 8. 为什么目前还不能直接算“结题完成”

虽然中期闭环已经成型，但如果以“完成毕业设计结题”为标准，当前还有三个层面的空缺。

### 8.1 功能层面还有扩展空间

目前仍缺少一些很容易被评审追问的点：

- 删除语义
- 恢复语义
- 范围查询
- 更完整的 compaction 解释能力

### 8.2 系统表达层面还没有完全收口

也就是：

- 最终版本基线还没有完全定稿
- README 仍偏中期风格
- 架构图、流程图、结题说明还不够集中

### 8.3 学术叙事层面还可以再加强

当前实验已经能支撑“中期展示”，但如果要更稳妥地服务结题，最好再强化：

- 为什么选这些 workload
- 为什么这些指标足以说明策略差异
- 当前教学型简化与工业系统的边界在哪里

## 9. 这份重建规划对后续结题的启发

从这 11 个 task 的结构看，项目的后续工作不应该再是无序加功能，而应该顺着原有路线自然延长。

最合理的延长方式是：

### 方向 A：补一个更完整的存储语义点

优先候选：

- `tombstone` 删除语义

原因：

- 与 LSM 本身高度相关
- 能自然延伸到 flush、read、compaction
- 能作为论文中“功能进一步完善”的亮点

### 方向 B：补一个更完整的可靠性点

优先候选：

- WAL recovery / replay

原因：

- 能解释“为什么要 WAL”
- 能把当前 append-only 的阶段限制补成更完整闭环

### 方向 C：补一个更强的展示点

优先候选：

- 前端增加 SSTable/compaction 的过程型可视化

原因：

- 更利于答辩展示
- 技术风险相对低于大改后端机制

## 10. 建议的结题扩展策略

如果目标是“在当前基础上继续扩充功能完成结题”，我建议沿这条线推进：

### 第一步：固定中期成果基线

- 以 `codex/task11-experiments-midterm` 为当前事实版本
- 把中期任务脉络文档整理齐
- 明确哪些内容是现状，哪些是下一步扩展

### 第二步：只选择一个主增强方向

推荐优先级：

1. `tombstone`
2. WAL recovery
3. 前端增强

原因：

- 这样能最大化保留现有任务链的连贯性
- 同时把新增功能控制在可结题的风险范围内

### 第三步：围绕新增功能补测试、可观测性和展示材料

也就是说，新增功能不应该只停留在“代码写完”，还应该同步补：

- 单元测试
- API 或前端入口
- metrics/trace 观察点
- 论文里的说明文字和实验设计

这其实也是前 11 个 task 已经体现出来的工作风格。

## 12. 重建后的总体判断

这 11 个 task 的规划并不是随意拆分的，而是非常清楚地沿着下面这条主线推进：

1. 搭骨架
2. 立模型
3. 补核心路径
4. 做策略差异
5. 加观测能力
6. 做服务入口
7. 做前端展示
8. 做实验结论

所以，后续如果我们要继续扩充功能完成结题，最好的策略不是推翻重来，而是继续顺着这条线往下长：

- 保留教学型 LSM 模拟器的定位
- 只补 1 到 2 个高价值增强点
- 把新增能力也纳入“测试 + 可视化/导出 + 文档 + 实验”的统一闭环

一句话总结：

这份重建后的总规划说明，项目当前已经完成了“中期可演示闭环”，而结题阶段的正确方向，是在这条已经跑通的主线上继续补强关键功能与材料，而不是重新发散。
