# 中期后至结题阶段详细计划清单

## 1. 制定本计划的依据

本计划同时基于三类信息形成：

- 开题报告中的研究目标、研究内容、技术路线与预期成果
- 中期报告中已经确认的阶段成果、存在问题与后续方向
- 当前仓库的实际实现状态、实验结果和文档沉淀情况

从这三类信息综合判断，项目当前已经完成了一个质量较好的中期闭环：

- 后端已具备教学型 LSM-Tree 的核心机制
- 前后端和可视化链路已经跑通
- 实验脚本与实验输出已经具备可复现基础
- 中期答辩所需的“系统演示 + 策略对比 + 结果解释”已经成立

因此，结题阶段的核心任务不再是“继续从 0 到 1 做功能堆叠”，而是围绕以下四个目标收口：

1. 把当前原型从“中期可演示”提升为“结题可论证”
2. 把临时实现、教学型简化与系统边界解释清楚
3. 把实验链路从“能跑”提升为“可信、规范、可引用”
4. 把论文、答辩与仓库展示三者统一起来

## 2. 当前系统状态判断

### 2.1 已完成且可作为结题基础的部分

- 单机版 LSM-Tree 教学模拟器主流程
- `put / get`
- WAL 追加写
- MemTable
- Flush 与 Level 0 SSTable 落盘
- 简化版 Bloom Filter
- STC 与简化版 LCS
- Metrics / Trace 导出
- FastAPI REST + WebSocket
- Vue3 最小可演示前端
- Docker Compose 启动
- 多组 workload 与策略对比实验

### 2.2 当前实现中明确属于“教学型简化”的部分

- WAL 仅追加写，不支持恢复与重放
- MemTable 使用 `dict`，不是跳表
- SSTable 使用 `JSONL + metadata JSON`
- Compaction 同步执行，不是后台异步调度
- LCS 为简化版实现，高层触发逻辑较粗糙
- 读放大 / 写放大属于模拟统计口径，不是硬件级真实 I/O
- 未实现 tombstone 删除语义
- 未实现范围查询

### 2.3 当前已经暴露出的结题阶段关键问题

- 某些中期阶段的实现虽然能用，但论文层面的解释仍不够严谨
- 部分指标定义与标准数据库文献中的常见含义并不完全一致，需要重新命名或补充说明
- LCS 的高层触发逻辑目前更接近“按表数量上限触发”，与“按层大小阈值触发”的标准叙述存在偏差
- 前端页面虽能展示，但仍然带有明显的中期“最小演示”痕迹，结题阶段需要进一步增强叙事完整性
- 实验结果已经形成，但离“论文可直接引用的规范实验材料”还有一段距离

## 3. 结题阶段总策略

## 3.1 建议采用的主线

建议结题阶段采用以下主线：

- 主线一：稳定当前系统基线
- 主线二：补强一个最有价值的系统增强点
- 主线三：强化实验、图表、结果解释和论文证据链
- 主线四：统一答辩展示与仓库最终交付形态

不建议继续并行推进多个高风险功能点。

### 3.2 推荐路线：系统完整性优先

在“继续增强系统功能”的候选项中，优先推荐把 **WAL recovery / replay** 作为结题阶段唯一重点增强项，而不是同时去做 tombstone、范围查询和复杂 compaction。

推荐理由：

- 它与现有写路径直接衔接，逻辑闭环自然
- 它可以显著提升系统完整性
- 它容易写出“系统可靠性与状态恢复”的论文论述
- 相比 tombstone 全语义或更复杂 LCS，风险更可控

如果你希望强调“存储语义完整性”，则 tombstone 可以作为备选增强项，但不建议与 WAL recovery 并行。

## 4. 结题阶段任务分层

以下任务按优先级划分为三层：

- P0：必须完成，否则会直接影响结题质量
- P1：强烈建议完成，会显著提升论文与答辩质量
- P2：可选增强，取决于时间余量

## 5. P0 必做任务清单

### P0-1 统一最终基线与版本说明

目标：

- 明确 `master` 为最终持续开发基线
- 明确当前系统实现边界、支持能力与未实现项
- 防止论文、答辩、仓库展示三套口径不一致

任务：

- 整理并更新总览文档，明确当前版本能力
- 在 README 中补全“教学型模拟器边界说明”
- 补全“当前实现与标准 LSM/工业实现差异说明”
- 为关键模块补一页架构总览文档

产出物：

- 项目总览文档
- 最新 README
- 架构说明文档

验收标准：

- 任何阅读仓库的人都能在 5 分钟内理解项目做到了什么、没做到什么、为什么这样设计

### P0-2 清洗和校正指标定义

目标：

- 把当前 metrics 口径说清楚
- 识别哪些指标名称容易误导论文读者

当前问题：
（已经完成）
- `read_amplification` 混入了 compaction 输入读
- `write_amplification` 是“模拟写次数 / put 数”，不是字节级写放大
- 指标定义目前适合教学展示，但论文中如果不加解释容易被误读

任务：

- 重新梳理 metrics 定义
- 在文档中明确区分：
  - 模拟统计值
  - 实际文件计数值
- 如必要，可将现有指标重命名为：
  - `simulated_read_amplification`
  - `simulated_write_amplification`
- 或保留原名，但在导出文件和论文中给出严格定义

产出物：

- 指标定义说明文档
- README / docs 补充说明
- 如有必要，对导出字段做兼容性调整

验收标准：

- 论文中每个指标都能给出一致、无歧义的定义

### P0-3 规范化实验材料

目标：

- 把“实验能跑”升级为“实验结果可引用”

任务：

- 固定最终实验矩阵
- 明确每组 workload 的用途
- 固定推荐展示的两组或三组实验
- 增加结果图表生成脚本
- 为每组实验保存：
  - 配置
  - workload
  - summary
  - trace
  - metrics
  - 图表

推荐最终保留的核心实验：

- 长写入压力对比：`write_heavy_long + aggressive_compaction`
- 重叠范围对比：`range_overlap_stress + overlap_pressure`
- 热点更新补充：`overwrite_hotspot + aggressive_compaction`

产出物：

- 最终实验结果目录
- 图表 PNG / SVG
- 实验说明文档

验收标准：

- 任何一组核心实验都可一键复跑并得到一致格式的结果输出

### P0-4 完成论文与答辩主材料骨架

## 6. P1 强烈建议任务清单

### P1-1 实现 WAL recovery / replay

目标：

- 补齐“写入后系统重启如何恢复”的闭环

建议范围：

- 启动时读取 WAL JSONL
- 按顺序回放记录恢复 MemTable
- 恢复最近的 `seq`
- 提供 reset / recovery 场景测试

注意：

- 不必引入工业级 checkpoint 机制
- 不必处理复杂崩溃一致性
- 重点是“教学上可解释、系统上可验证”

产出物：

- WAL recovery 模块
- 单元测试
- 恢复过程说明文档
- 恢复场景演示脚本

验收标准：

- 给定 WAL 文件，系统重启后能恢复 MemTable 状态并继续写入

### P1-2 修正 LCS 触发口径与论文叙述偏差

目标：

- 让 LCS 更接近开题和论文中的描述

当前问题：

- `level_size_multiplier` 目前实际控制的是高层表数量阈值
- 更标准的 LCS 通常强调“层总大小阈值”

建议改造方式：

- 不追求工业级 LCS
- 只把高层触发条件从“表数上限”改成“层总记录数上限”或“层总字节上限”
- 保留简化版 overlap merge 逻辑

这样做的好处：

- 更贴近“每层容量扩大固定比例”的论文叙述
- 更容易解释 `level_size_multiplier`
- 有助于让实验结果更符合直觉

验收标准：

- `level_size_multiplier` 的含义与文档叙述一致
- LCS 在高层的触发逻辑更合理

### P1-3 前端补齐“读路径与策略解释”展示

目标：

- 让前端不仅能看写路径，也能解释查询路径

任务：

- 展示 `get` 的命中路径
- 展示 Bloom hit / miss
- 展示最近一次 compaction 的输入输出表
- 在页面上增加“当前配置说明”和“当前策略说明”

建议风格：

- 不追求复杂动画
- 追求可解释性和截图友好

验收标准：

- 前端页面能够支持答辩中完整讲解一次 `put/get/flush/compaction`

### P1-4 统一 API 与 WebSocket 事件语义

目标：

- 让 REST 状态查询与 WebSocket 事件结构保持一致

任务：

- 梳理事件字段
- 统一状态字段命名
- 补全“事件 -> 前端展示 -> 实验导出”的一一对应关系

验收标准：

- 同一个系统动作在 trace、ws、state 中没有互相矛盾的命名或含义

## 7. P2 可选增强任务清单

### P2-1 tombstone 删除语义

适用前提：

- 只有在 WAL recovery、实验和论文主线都已经稳定之后才建议做

价值：

- 能提升“存储语义完整性”
- 适合在论文中作为增强点描述

风险：

- 需要修改 Record/WALRecord/get/compaction/实验解释
- 比 WAL recovery 更容易引入连锁复杂度

结论：

- 可做，但不应与 WAL recovery 并行作为双主线

### P2-2 范围查询

价值：

- 可以展示 SSTable 有序性

风险：

- 与本课题中期和现有实验主线关系较弱
- 论文价值不一定高于恢复或删除语义

结论：

- 不建议作为结题阶段优先增强点

### P2-3 前端高级可视化

价值：

- 提升答辩观感

风险：

- 容易花时间但不显著提升论文质量

结论：

- 只做轻量增强，不做大规模前端重构

## 9. 不建议做的事情

以下事项在结题阶段不建议同时推进：

- 同时做 WAL recovery 和 tombstone 大改
- 同时重写 LCS、增加范围查询并大改前端
- 以工业级数据库为目标继续扩展底层复杂度
- 在实验口径未稳定前反复改 metrics 定义

原因很直接：

- 这些工作彼此耦合度高
- 容易引发测试、实验结果和论文叙述同时变化
- 会把结题阶段从“收口”重新拖回“发散开发”

## 11. 结论

从开题报告的目标和中期阶段的实际成果来看，你当前项目已经完成了“教学型 LSM-Tree 可视化与交互式模拟系统”的最难部分，即系统主流程、前后端闭环和基础实验框架。结题阶段最重要的不是继续无边界加功能，而是围绕“系统完整性、实验可信性、论文表达力、答辩展示力”做有控制的增强与收口。

4. 再决定是否补 tombstone 作为额外亮点

这条路线风险最低，也最容易把现有成果稳定转化为结题质量。
